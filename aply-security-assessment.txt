1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Aply is a live hiring platform ("where tomorrow is hired") for Gen Z talent.
The classic web/data-exposure surface is reasonably hardened (Firebase
Firestore/RTDB/Storage are locked down; API routes require auth). However,
source review of the client bundle reveals that several SECURITY-CRITICAL
STATE TRANSITIONS ARE PERFORMED CLIENT-SIDE in Firestore, which is a strong
indicator of business-logic bypass if security rules are not strict.

  F4 MEDIUM    Unauthenticated, unrate-limited LLM proxy endpoints on aply-server
               -> cost/resource abuse and business-logic oracle.
  F5 LOW       Firebase Auth user enumeration enabled (email enumeration).

F1 [CRITICAL] Client-side self-assignment of paid/accepted application state
--------------------------------------------------------------------------------
Type      : Business logic / authorization (payment bypass)
Location  : /assets/Pipeline-Jc2L2Pp1.js
Status    : Code-evidenced. Exploitability depends on Firestore rules (unverified).

Evidence (de-minified logic):
    Y = () => doc(db, "Applications", `${Op(email)}_${pipelineId}`)
    H = () => {
      const q = Y();
      !q || !i || setDoc(q, {
          pipelineId: S,
          email: r.email,
          userId: i,
          paymentStatus: "balance_paid",     // <-- paid flag set by client
          decisionStatus: "active",          // <-- accepted flag set by client
          submittedAt: serverTimestamp(),
          updatedAt: serverTimestamp()
        }, { merge: true })
        .catch(ce => console.error("UGC join write failed", ce));
    }

The paid-access gate reads these same fields client-side:
    const paid = ["deposit_paid","balance_paid"].includes(paymentStatus);
    const accepted = ["accepted","active"].includes(decisionStatus);
    const unlocked = paid && accepted;

Alias verification (rigorous):
    In /assets/Pipeline-Jc2L2Pp1.js import list: "al as xt", "i as V".
    Main bundle export table: "al" <- local "Vu".
    Function Vu(...) constructs a mutation with the literal string "setDoc":
        function Vu(e,t,n){ ... I0(ad(r),"setDoc",e._key,o,...) }
    => xt === setDoc, and V("Applications", id) === doc(db,"Applications",id).

Impact:
    A candidate can write balance_paid + active to their own application and
    unlock the "$20/hr paid contract" / paid course without paying, defeating
    the "only pay for results" business model. Enables fraudulent accepted
    status (contract/payroll fraud) and revenue loss per user.

Preconditions / why it matters:
    The feature itself performs this write from the browser, so Firestore rules
    must permit the authenticated applicant to write these fields for the flow
    to function. If rules do not explicitly pin paymentStatus/decisionStatus,
    the bypass is available.

Steps to validate (ONLY with authorization + a test account):
    1. Register a test user.
    2. Open a pipeline and trigger the "join"/"UGC join" action.
    3. Inspect the Applications/{normalize(email)}_{pipelineId} doc.
    4. Confirm paymentStatus/decisionStatus are "balance_paid"/"active".
    5. Compare access before/after (paid course/contract view).
    6. (Do NOT modify real applicant records.)

Remediation:
    - Move state transitions to a trusted server / Cloud Function using the
      Admin SDK with payment-provider verification.
    - Firestore rules: deny client writes to paymentStatus, decisionStatus,
      and any entitlement fields; allow only specific fields to the owner.
    - Prefer server-issued custom claims for entitlements.

F2 [HIGH] Admin / chapter-admin authorization is client-controlled
--------------------------------------------------------------------------------
Type      : Privilege escalation / broken authorization
Location  : chunks (sorority/chapter, admin, course) e.g. useCreatorPortfolios,
            UgcApprovalsAdmin, CourseAdminPage, chapter code
Status    : Code-evidenced. Server-side enforcement unverified.

Evidence:
    Hardcoded client-side admin allowlist (two copies found):
        const k = ["nd@aply.com"];
        const T = e => !!e && k.includes(e.toLowerCase());
    UI gate uses it:
        ... "admin" : "denied"
    (Also: admin identity "nd@aply.com" is disclosed.)

    Roles are written by the client with merge via setDoc:
        setDoc(memberRef, {
            role: "leadership",
            isAdmin: <bool>,
            joinedAt: ...
        }, { merge: true })

    Admin screens gated only in the SPA:
        /admin/ugc-approvals
        /admin/course/:courseId

Impact:
    If rules trust client-written role/isAdmin, any authenticated member can
    elevate to chapter leadership/admin, then approve UGC, edit courses, and
    manage chapters (content integrity, unauthorized messaging to students).

Remediation:
    - Use Firebase custom claims (admin:true, chapterId, role) set server-side.
    - Rules must check request.auth.token.admin / role, never Firestore fields
      writable by the user.
    - Remove hardcoded admin emails from the client bundle.

F3 [HIGH] Predictable Application document IDs -> applicant IDOR / PII exposure
--------------------------------------------------------------------------------
Type      : IDOR / data exposure
Location  : /assets/Pipeline-Jc2L2Pp1.js  (Op normalizer) and Applications reads
Status    : Code-evidenced. Read scope depends on Firestore rules (unverified).

Evidence:
    Op = (n="") => n.toLowerCase().replace(/[^a-z0-9]+/g,"_").replace(/^_+|_+$/g,"")
    doc id = `${Op(email)}_${pipelineId}`

    Application docs contain: pipelineId, email, userId, paymentStatus,
    decisionStatus, submittedAt, updatedAt (and portfolio/UGC data).

Impact:
    Document IDs are derivable from an email + pipelineId (no randomness), and
    the collection holds candidate PII + hiring decisions + payment state.
    If rules allow reads by any authenticated user (common misconfig), an
    attacker can enumerate/read other applicants' records.

Remediation:
    - Use random document IDs (Firestore auto-ID) for applications.
    - Rules: read only by owner (request.auth.uid == resource.data.userId) or
      authorized employer for that pipeline.
    - Avoid PII in document IDs (they can appear in logs/URLs).

2.4 [HIGH] Unauthenticated Stripe checkout creation + client-controlled
    applicationData and returnUrl
  Location: PaymentPortalPage chunk; route /pay?app=<b64url>&return=<url>
  Client code (PaymentPortalPage-Ci2nqhbt.js):
    const U = s => { ... atob(base64url(s)) ... JSON.parse(...) };   // ?app=
    const L = () => { const [t]=useSearchParams(); return ...
      pipelineId: slug, applicationData: decode(t.get("app")),
      returnUrl: t.get("return") };
    fetch(`${server}/api/stripe/create-checkout-session`, {
      method:"POST", headers:{"Content-Type":"application/json"},
      body: JSON.stringify({ pipelineId, applicationData, returnUrl })
    })                                   // <-- NO Authorization header

  Results / risk:
    - applicationData is base64url JSON fully controlled by the URL and sent
      unauthenticated. It is the applicant identity payload tied to the $99
      deposit. Attacker can forge/alias applicant data or attribute a payment
      to arbitrary values.
    - returnUrl is client-supplied and forwarded to Stripe session creation.
      If not strictly allow-listed, it is an open redirect after payment
      (phishing). Needs safe validation with owner permission (would create a
      real Stripe session to confirm).
    - No auth => session-creation spam / abuse.
    - Price itself appears fixed server-side ($99 deposit, $400 balance in the
      hardcoded portal config), so direct amount tampering is not evident from
      the client, but server trust of applicationData is a real concern.

  Fix: authenticate + rate-limit; validate returnUrl against an allowlist;
  derive applicant identity from the authenticated user, never from ?app=.
